# КТ1

Публичный отчёт по лабораторной работе. В репозитории — само задание, конфигурация Terraform, ответы на контрольные вопросы и место для скриншотов.

## Цель

Изучить концепцию «Инфраструктура как код» (IaC) и развернуть локальные сервисы в Docker декларативным кодом Terraform: веб-сервер Nginx и базу Apache CouchDB.

## Задание

Модернизировать базовый манифест Terraform: убрать жёстко прописанные параметры и добавить новые ресурсы.

1. Вынести внешние порты и имена контейнеров во входные переменные.
2. Рядом с Nginx развернуть второй контейнер — Apache CouchDB, образ `couchdb:3.3`.
3. После `terraform apply` вывести в консоль готовые URL:
   - Nginx: `http://localhost:8080`
   - админ-панель CouchDB: `http://localhost:5984/_utils/`

Базовый пример из методички поднимает один контейнер Nginx (`nginx:latest`) и пробрасывает порт контейнера 80 на порт Windows 8080. В этой работе к нему добавлены переменные, CouchDB и outputs.

Учётные данные CouchDB взяты из методички и нужны только для локальной учебной базы: пользователь `admin`, пароль `password_student`.

## Зеркало провайдеров

Официальный реестр `registry.terraform.io` с российских IP часто недоступен. Terraform направлен на зеркало Яндекса.

На Windows Terraform читает файл:

`C:\Users\<пользователь>\AppData\Roaming\terraform.rc`

Содержимое (блок один раз, без повтора):

```hcl
provider_installation {
  network_mirror {
    url     = "https://terraform-mirror.yandexcloud.net/"
    include = ["registry.terraform.io/*/*"]
  }
  direct {
    exclude = ["registry.terraform.io/*/*"]
  }
}
```

Путь `~/.terraformrc` из текста на портале — это домашний каталог Linux и macOS. На Windows ему соответствует `%APPDATA%\terraform.rc`.

## Как повторить

Нужны включённая виртуализация, запущенный Docker Desktop и Terraform в `PATH`.

```powershell
cd kt1-iac
terraform init
terraform apply
```

На вопрос подтверждения ввести `yes`.

Проверка в браузере:

- http://localhost:8080 — страница Welcome to nginx
- http://localhost:5984/_utils/ — админ-панель CouchDB (логин `admin`, пароль `password_student`)

Повторный `terraform apply` без правок кода изменений не делает: инфраструктура уже совпадает с манифестом.

После скриншотов контейнеры удаляются:

```powershell
terraform destroy
```

И снова `yes`.

Порты и имена можно переопределить без правки кода, например:

```powershell
terraform apply -var="web_port=8081" -var="web_container_name=nginx_lab"
```

## Ответы на контрольные вопросы

### 1. В чём разница между декларативным и императивным подходами?

Императивный подход описывает шаги: скачать, распаковать, запустить. Так устроены Bash и PowerShell. Если шаг обрывается, система остаётся в промежуточном состоянии, и следующий запуск легко ломается о то, что уже сделано.

Декларативный подход описывает конечный результат: контейнер Nginx на порту 8080 и CouchDB на порту 5984. Terraform сам сравнивает этот результат с тем, что уже есть, и выполняет только недостающие действия. Порядок «как именно ставить» в коде не расписывается.

### 2. Что такое идемпотентность в IaC?

Идемпотентность — это одинаковый итог при повторных запусках и отсутствие лишних побочных эффектов. Первый `terraform apply` создаёт контейнеры. Следующие запуски при том же коде сообщают, что изменений нет: второй Nginx и вторая база не появляются. Императивный скрипт на повторном создании папки или контейнера чаще падает с ошибкой «уже существует».

### 3. Зачем нужен файл terraform.tfstate?

Это слепок реального мира, а не ещё одна копия манифеста. После создания контейнера Terraform записывает туда его идентификатор и параметры. На следующем запуске он сверяет код, этот файл и живой Docker и понимает, что уже создано, что изменилось и что надо удалить. Файл нельзя удалять или править вручную: без него Terraform потеряет связь с уже созданными ресурсами. Поэтому состояние не коммитится, а манифесты в Git — коммитятся.

### 4. Что произойдёт, если запустить terraform apply там, где контейнер Nginx уже развёрнут?

Если код не менялся, план пустой: Terraform увидит контейнер в state и в Docker и напишет, что инфраструктура совпадает с конфигурацией. Повторно контейнер не создаётся.

Если в коде изменился порт, имя или появился новый ресурс (как CouchDB рядом с уже запущенным Nginx), apply затронет только эту разницу: поправит Nginx или добавит базу, не пересоздавая всё подряд без причины.
